# 项目决议日志技能

把会议录音笔记里的结论提炼成项目长期维护的决策账本。核心价值：用项目上下文修正录音软件的转写错误（它不懂项目专有名词），再把结论沉淀成可追溯的 changelog。

## 职责边界

- ✅ 做：转写校验 → 四类提炼 → 追加到决议日志
- ❌ 不做：语音转写（录音软件已完成）、待办状态追踪、更新其他项目文档

## 决议日志位置

`docs/VeryFood-项目决议日志.md`

文件不存在时，先用「日志骨架」（见文末）初始化，再追加第一条。

---

## 处理流程（严格按顺序执行）

### 第一步：建立项目术语基准

读取 `docs/` 下的项目文档（立项书、产品方案、决议日志本身），抽取专有名词清单，作为后续校验的基准：

- **产品/项目名**：VeryFood（不要写成"瑞福"）、VeryFoodAI 工作台
- **技术术语**：RAG、微调、reward mechanism、配方生成、合规校验、知识检索
- **人名/机构**：麻生、集美大学、孙院长
- **模块名**：新品全链路研发、多国合规校验、市场情报分析、食品知识问答

术语是演进的——每次运行时以项目文档的最新内容为准，不要用记忆里过时的清单。

### 第二步：转写校验

录音软件做的是通用模糊匹配，不懂项目专有名词，会把术语转错（如 `protein`→`prodeen`、`VeryFood`→"瑞福"）。这一步用项目上下文修正。

**扫描范围**：会议 md 的"原文"部分是主战场；同时检查"智能总结"部分——它是基于错误原文生成的，错误会传染进去，需对照校验后的原文一并修正。

**识别可疑词**：
- 英文乱码（prodeen、reawrd、fintune）
- 音近中文字（瑞福→VeryFood、麻省→麻生）
- 生造词、与上下文明显不通顺的词

**修正原则**：
1. 用术语基准 + 上下文语义判断正确写法
2. 只改明确的转写错误，不改写会议原意
3. **不确定的不要瞎改**——标记 `[存疑：原文"普鲁汀"，疑似 protein？请确认]` 让用户定夺

**校验完先报告，不偷偷改**：列出所有改动清单给用户确认，格式如下：

```
📋 转写校验报告（共修正 N 处）
1. 原文 "prodeen" → protein（项目术语）
2. 原文 "瑞福" → VeryFood（产品名）
3. 原文 "奖励机制" → reward mechanism（结合上下文，指 RLHF 的奖励机制）
4. [存疑] 原文 "普鲁汀" → 疑似 protein？请确认
```

用户确认后，再进入提炼。这一步是为了避免把错误固化进决议日志——日志是长期账本，错一个术语以后全错。

### 第三步：四类提炼

基于校验后的全文，按四个维度提炼：

| 维度 | 识别标准 |
|------|---------|
| **🆕 新方向** | 之前没有的、新增的产品/技术/合作路线 |
| **🔄 需求变更** | 对已有功能/计划/决策的修改、调整、推翻。**必须写清"从 X → Y"** |
| **📋 待办** | 明确的动作项，带执行人线索。无执行人写 `@未指派` |
| **⚠️ 风险/待定** | 尚未解决的问题、依赖外部条件的事项、已识别但未拍板的风险 |

**提炼原则（严格遵守）**：

1. **只记实质内容，不记过程**——"决定 X""要解决 X"才算；"讨论了 X"、寒暄、演示流程、背景铺垫全部丢弃。
2. **每条一句话能说清**——保持决策颗粒度，不展开论证。详细背景留在会议原文，日志只放结论。
3. **待办尽量带执行人**——会议里提到"谁去做"就记上；没提到标 `@未指派`。
4. **变更必须写"从 X → Y"**——只写新值不算变更，必须体现改了什么。
5. **区分"决定"和"讨论"**——明确拍板的进新方向/需求变更；只是聊到、没结论的进风险/待定。
6. **追加前查重**——先扫一遍决议日志已有内容，如果某条方向之前已记录过，不重复写入（避免日志膨胀）。

### 第四步：追加到决议日志

把提炼结果按「单次条目模板」格式化，追加到 `docs/VeryFood-项目决议日志.md`。

**追加规则**：
1. **时间正序**——新的条目加在文件末尾，不是开头。
2. **空节写"无"**——某类无内容时写"无"，四节永远齐全，结构一致。
3. **纯追加，不改历史**——只往末尾加，绝不修改已存在条目（除非用户明确要求）。历史决议是留痕的，改了就失去账本意义。

## 单次条目模板

```markdown
## YYYY-MM-DD 会议主题

**来源**：[会议文件名](meetings/会议文件名.md)
**时间**：YYYY-MM-DD
**参与**：人员列表（从会议信息抽取，无则标"未记录"）

### 🆕 新方向
- 方向描述（一句话）

### 🔄 需求变更
- 功能/计划：从 X → Y

### 📋 待办
- [ ] 待办内容 @执行人（无则 @未指派）

### ⚠️ 风险/待定
- 风险/待解决问题描述
```

## 完整示例

输入：`docs/meetings/VeryFood垂直AI食品研发工作台项目讨论-2026年06月12日-来自【Get 笔记】.md`

提炼后追加的条目：

```markdown
## 2026-06-12 集美大学合作讨论

**来源**：[VeryFood垂直AI食品研发工作台项目讨论-2026年06月12日](meetings/VeryFood垂直AI食品研发工作台项目讨论-2026年06月12日-来自【Get 笔记】.md)
**时间**：2026-06-12
**参与**：孙院长、两位教授、两位博士、赵医生

### 🆕 新方向
- 分类目精细化训练，先做烘焙类验证路径再拓展其他类目
- 计划与高校共建 AI 食品研发中心，依托高校获取专业数据集和专家支持

### 🔄 需求变更
- 定价建议模块：从"配方生成后调用" → "市场洞察之后调用"（先取目标渠道价格再生成配方）

### 📋 待办
- [ ] 高校专家会后确认本校合作规定 @高校专家
- [ ] 选定一个小类目结合现有资源启动训练 @团队

### ⚠️ 风险/待定
- 公开数据集质量差（存在"油脂解酒"等错误知识），需补充专利库等非开源专业数据
- 原料价格初期允许 20-30% 误差，后期需接入供应商实时价盘
- 训练核心难点：reward mechanism 设计，需专业工程人员多轮干预
```

注意示例中 `reward mechanism` 是校验后的写法（原文可能被转成"奖励机制"或乱码）；定价模块那条体现了"从 X → Y"的变更写法。

## 日志文件骨架（首次创建时）

当 `docs/VeryFood-项目决议日志.md` 不存在时，先写入：

```markdown
# VeryFood 项目决议日志

> 本文档长期维护，记录项目的产品方向、需求变更、待办、风险。
> 每次会议后由 project-decision-log skill 追加，按时间正序排列。
> 会议原文见 docs/meetings/。

---
```

然后追加第一条条目。

## 给执行者的备忘

- 你是运行在项目里的，能读到所有项目文档——这是你比录音软件强的核心优势，校验时要用足。
- 校验报告是给用户看的，不是给自己看的——列清楚、排版好，让用户一眼能确认。
- 提炼是判断密集型工作，不要偷懒抄会议原文的原话——要压缩成一句话的结论。
- 日志是长期资产，宁可少写一条精确的，不要多写一条啰嗦的。
